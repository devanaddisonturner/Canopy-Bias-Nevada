## The three optional paths, decided

### 1. Figure resolution: raised, and EPS deliberately avoided

**Decision: every figure ships .tif, .png and .pdf. Figures 1, 2 and 4 at 600 dpi
with vector PDFs; Figure 3 at 300 dpi, which is its ceiling. No EPS.**

The rule is 1200 dpi for line art, 600 for grayscale, 300 for colour. All four
figures are colour and met 300 dpi, so they complied. But a colour *line* drawing
can be read under the 1200 clause, and if a production editor reads it that way the
result is a round trip at proofing, so the drawn figures carry a vector PDF that
settles it.

| Figure | Type | Raster | Vector PDF |
|---|---|---|---|
| 1 Study area | colour **line art**, not imagery | **600 dpi** | **vector**, 1 colourbar raster |
| 2 Construction of the bound | colour line art | 600 dpi | fully vector |
| 3 Canopy at two matched parcels | colour **imagery** | 300 dpi, its ceiling | 6 embedded rasters |
| 4 Bound against product | colour line art | 600 dpi | fully vector |

**Figure 1 was misclassified until 29 September 2026.** It shipped at 300 dpi with
no PDF, on the reasoning that it is "photographic raster content". It contains no
imagery: the scatter, the outline, the inset and the type are all drawn. Saving it
as a PDF and counting image objects returns exactly one, a 648 x 39 greyscale
colourbar strip. So it belongs in the same class as Figures 2 and 4 and is now
treated the same way.

**Figure 3's 300 dpi is arithmetic, not a lower standard.** Its grid spans 6.552 in
across three panels, so each prints 2.107 in wide, and the Earth Engine exports
behind them are 633 px. 633 / 2.1068 = 300.5 dpi, so a 300 dpi save renders
each panel within one pixel of its source. A 600 dpi save would upsample 633 px to
1264 px: double the bytes, no added detail. Re-derive that before changing it.

Each figure script declares its dpi in one `DPI` constant, and `make_tables.py`
reads the constant out of the script and checks the files carry it, so a script
edited without regenerating its outputs fails.

**The EPS finding matters.** PS is on the journal's preferred-format list, so
exporting EPS looks like the safe choice. It is not. matplotlib's PostScript
backend emits: *"The PostScript backend does not support transparency;
partially transparent artists will be rendered opaque."* Figure 4's shaded
band, which is the whole point of the panel, would become a **solid block
covering the curves**, and Figure 2's tinted panel would flatten too. The
damage would be silent. Use the PDF or the 600 dpi raster, never EPS, for
these two figures.

Layout is unaffected: images are placed at a fixed 6.5 inch width, so source
resolution changes nothing on the page. Verified: layout unchanged by the resolution rise. The manuscript is 23 pages.

### 2. Graphical abstract: made

**Decision: make one.** It is optional, but the journal's own figures say
articles carrying an extender are markedly more likely to be downloaded, and
the cost here was one short script.

`GraphicalAbstract1.png`, **525 x 388 px**, at the journal's maximum width and
named as the guidelines require. It is designed *for* 525 px rather than
shrunk from a print figure: one message, two series, large type, no tick
clutter.

It is generated by `make_graphical_abstract.py` **from the released row-level
data**, so its numbers cannot drift from the manuscript. The 12.1 point gap
and the 21,931 sample size it prints are both values the verification harness
asserts.

Submit it as a **separate file**, not embedded in the manuscript.

**PNG only. It does not need a .tif, and it must not have a .pdf.** The
guidelines permit exactly three formats for a graphical abstract, ".jpg, .png, or
.tif", and their rule on size is a *pixel* maximum of 525 px wide rather than a
dpi threshold, because this is a listing thumbnail and not print artwork. A vector
PDF has no pixel width to satisfy that with, and PDF is not on the list anyway.
The instinct to supply one comes from Figures 2 and 4, which do have PDFs, and it
does not carry over: those are print figures under a dpi rule. A .tif would be
allowed, but `.png` is on the same list, is lossless, is the size the image was
designed at, and the guidelines say to label the file `GraphicalAbstract1`,
singular, so a second file under that stem would only create an ambiguity about
which one is the graphical abstract.

All four of the guidelines' rules for a graphical abstract are now gated by
`make_tables.py` rather than left as prose here: the filename, the permitted
format, the exact 525 px width, and that it is not embedded in the manuscript. A
file named GraphicalAbstract1.pdf fails the run. It is written here without
backticks, because the check that every backticked filename in a shipped document
resolves inside the package caught this sentence: no such file exists, and none
should.

## Colour audit: three defects found, one of them serious

The palette had been chosen by eye and checked only loosely. Measuring it
properly, by simulating protanopia, deuteranopia and tritanopia with the
Vienot, Brettel and Mollon (1999) LMS method, found three problems.

| Where | Problem | Now |
|---|---|---|
| Figure 1 site markers | red on the darkest green of the canopy ramp: separation **8**, luminance contrast **1.30:1** | white casing; **7.6:1** |
| Figure 3 cell markers | same fault, separation **24**, contrast **1.45:1**, and worst in the closed-canopy panel the figure exists to show | white casing; **6.5 to 11.4:1** |
| Gap annotation | crimson `#a01b20` sat **39** from the product colour under tritanopia, below the threshold of 40 | deep maroon `#6B0F1A`; **72**, and 12.29:1 against white |

The two marker faults matter more than the annotation. Red at 1.30:1 against
dark green fails the 3:1 threshold for graphical objects for **every** reader,
not only colour-blind ones, and disappears entirely in greyscale printing. The
marker was least visible in exactly the panel that carries the paper's
argument. The markers stay red, as the captions describe them; the white
casing rescues them by luminance, which no colour deficiency affects.

The series pair was also changed, from `#1f4e79`/`#b8560f` to the Okabe-Ito
colour-blind-safe blue and vermillion, darkened to `#005A8F`/`#A8480A`. This
was an improvement rather than a fix: the old pair already cleared both
thresholds. Worst-case separation rises 110 to 129 and the product colour's
contrast rises 4.80:1 to 5.84:1.

`check_colours.py` now gates all of this as a third check alongside the numeric
harness and the layout checks. It reads the palette constants out of the figure
scripts rather than holding its own copies, and it confirms in the **rendered
pixels** that the white casing is really there, because `path_effects` is easy
to set and easy to have silently not apply. It was proved to fire on the
pre-fix scripts before being accepted, and it caught a bug in its own first
draft, which compared the blue against itself.

## Producing the files you upload

This document used to say nothing about where the upload files come from, which
left the one gap a submission-time checklist cannot afford: the archives are built
by a script now, and someone working from this page alone would assemble them by
hand.

```
bash build_package.sh      # the reproduction package, 67 files
bash build_submission.sh   # canopy_bias_submission.zip and canopy_bias_figures.zip
```

`canopy_bias_submission.zip` is what goes to the journal. Open the
README_submission.txt at its root first: it lists what to upload into which slot,
and it opens with what is still outstanding. `canopy_bias_figures.zip` is the same
seven figures on their own, for a system that wants them separately.
`build_submission.sh` runs the three gates before it builds anything and rereads
the archives afterwards, so an archive that disagrees with the working tree fails
rather than reaching an editor.

**The order matters, and it is not the obvious one.** `build_package.sh` ships
`README_submission.txt`, and `README_submission.txt` states the package's own file
count, so the two depend on each other:

1. `build_package.sh`, which establishes the package and its true file count.
2. If that count changed, correct it in `README_submission.txt`.
3. `build_submission.sh`, which builds the archives from the current READMEs and
   checks the stated count against the package.
4. `build_package.sh` once more, but only if step 2 changed anything, so the
   package ships the corrected README.

It converges there: step 4 changes the package's contents but not its file count,
so the archives stay correct. Running these in the wrong order is how the file
count and the archive READMEs drifted apart in the first place.
